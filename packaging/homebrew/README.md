# Homebrew formula preparation

`hollis.rb.in` is the prepared template for a future formula in the
`kamenxrider/homebrew-tap` tap. Publish runtime v0.7.1 first, authenticate its
assets and source commit, then update and publish the formula. The current
template is not a published 0.7.1 installation path. After that follow-up,
install with
`brew install kamenxrider/tap/hollis`. Render it only from a locally downloaded release set whose source ref, full commit,
signer workflow and `--deny-self-hosted-runners` attestation have already been
verified independently. The preparation script checks local manifest, asset,
bundle, bridge and checksum agreement; that offline check is not provenance
authentication.

The selected release must include the reviewed sidecar; older published releases
do not gain this record retroactively. Set the variables below to the exact
independently authenticated tag ref and full source commit.
For 0.7.0, the [authenticated pin refresh](../../scripts/release/README.md#installer-release-pins)
can render the formula together with the installer and plugin lock from the
same authenticated assets. Its checksum remains pending until that operation;
do not fill this template from a private build.

```sh
python3 scripts/release/verify_artifacts.py /path/to/verified-release \
  --source-ref "$HOLLIS_SOURCE_REF" \
  --source-commit "$HOLLIS_SOURCE_COMMIT"
python3 scripts/release/prepare_distribution.py /path/to/verified-release \
  --output /tmp/hollis.rb
```

The script renders a local formula only. It does not write to a tap, install Homebrew,
change global package-manager state, or run inference. Do not treat a locally
built candidate or an offline fixture as published provenance.

The formula keeps `hollis`, `hollis-native`, the bridge archive and the bundle's
existing `manifest.json` in one versioned `libexec` directory. Public `bin`
entries are symlinks into that directory. Completion files are generated by
`hollis completion` during formula installation. Homebrew uninstall removes its
keg but does not remove Hollis chats or configuration.

## Quick start

After installation on an Apple-silicon Mac running macOS 27 or later with
Apple Intelligence enabled and its model available, start with the native local
model:

```sh
hollis respond --model local "hello"
```

No Shortcuts imports are needed for `local`. Shortcuts imports are optional:
enable them only for Cloud, Cloud Pro, On-Device, ChatGPT or images. See
[selected-route diagnostics](../../docs/selected-route-setup.md) and the
[image setup guide](../../docs/image-generation.md#setup).
Run `hollis setup --import` to open all nine bundled imports, or
`hollis setup --import cloud chatgpt` for selected routes. It verifies the archive
against the installed manifest, signs private copies, skips bridges discovery
already finds installed (unless `--force`), and asks before opening any window.
Choose **Add Shortcut** in each window, then run `hollis doctor`.
Non-interactive, JSON and agent invocations require explicit `--yes`.
Installation does not import them or request inference.

For a brew install, `hollis setup --model local --json` returns
`runtime_unverified` (exit 10). This means setup lacks the fresh verified-runtime
record supplied by the plugin installation owner, not that Homebrew found
tampered files or that the local model cannot run. Homebrew installation does
not produce that record, and standalone receipt verification is not implemented.
Use `hollis doctor --model local --json` for read-only availability checks, then
run the local command above when you want inference. For an optional Shortcut
route, run `hollis setup --import cloud-pro` and use `hollis doctor --model cloud-pro --json`
(or the selected route). Doctor does not authenticate artifacts or prove
inference works. Reinstalling with brew does not satisfy setup's trust boundary;
do not fabricate a verification record.

## Background API

```sh
brew services start hollis
brew services stop hollis
```

The optional service runs `hollis serve --addr 127.0.0.1:1978 --no-auth`.
It never binds a remote address. Unauthenticated requests must pass loopback
Host/Origin checks, but any local process can use this API, including making
model requests. Starting a service does not import Shortcuts or make a model
request. Logs go to `$(brew --prefix)/var/log/hollis/stdout.log` and `stderr.log`.
Stop the service before upgrading and restart it afterwards.

For authenticated service operation, use a custom service plist whose
`ProgramArguments` replace `--no-auth` with `--token-file` and an absolute path
to a private mode-600 token file containing at least 32 bytes of token:

```sh
brew services start hollis --file=/absolute/path/hollis.plist
```

The [LaunchAgent template](../launchd/io.github.kamenxrider.hollis.serve.plist)
uses the same loopback endpoint with token-file authentication. Adapt its binary,
token and log paths for your installation and create the log directory first.
Never put a token value in a plist. See [server setup](../../docs/serve.md).

## Upgrades and verification

Close any running `hollis serve` or chat before upgrading. Upgrading from v0.4.0
runs a one-way database migration from schema v2 to v3 when the new runtime first
opens the database. Returning to v0.4.0 afterwards requires the documented
[backup-recovery procedure](../../docs/cli.md#database-upgrades-and-recovery);
restoring a pre-upgrade snapshot loses later changes. `brew cleanup` removes the
old version, not the migration. Uninstall retains chats and configuration, and
does not remove manually imported Shortcuts.

The formula checks bundle-internal hashes only; it does not verify GitHub build
attestations. The [curl installer](../../scripts/install.sh) remains the route
that verifies those attestations when `gh` is installed. Without `gh`, it
requires a release-pinned bundle SHA-256 and checks `SHA256SUMS`, but does not
verify build provenance. The native helper is ad-hoc signed, not
Developer ID signed or notarized.

## Local validation

`packaging/homebrew/test_formula_lifecycle.py` has tested formula installation
and its lifecycle against a real Homebrew executable in disposable, isolated
prefixes: a clean install with generated
completions, symlinked sibling-helper invocation, tampered-helper rejection,
upgrade and uninstall that retain conversations and configuration byte for
byte, and a prefix path containing spaces. Installing from a published tap
into a real user Homebrew, verifying actual published downloads and
fresh-account onboarding remain unverified, and real package-manager testing
stays in isolated prefixes.

Both fixture version labels are built from the checkout under test. These tests
check package upgrade preservation, not migration from a released v0.4.0 executable.

Run the six lifecycle tests on a Mac with Homebrew, Go, a configured Git commit
identity and the macOS 27 SDK:

```sh
python3 -m unittest discover -s packaging/homebrew -p 'test_*.py' -v
```

The clean-install test also runs `brew audit --strict --formula` on the rendered
formula in the disposable local tap, using its GitHub release URL rather than
the loopback fixture URL. It omits `--online`; it does not qualify published
downloads or run livecheck against GitHub. Homebrew's installed Ruby and audit
gems are copied into the disposable prefix. Homebrew may download missing
audit gems and core audit data into that prefix. Temporary taps and kegs are
removed with the prefix, including on setup failure. Set `TMPDIR` to choose the
temporary parent.
